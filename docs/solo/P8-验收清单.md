## 逐条说明

### 1 · 3 分钟建单

从点「＋ 建一单」到卡片出现在时间轴上：选客户（搜昵称）→ 选款式 → 定时间 → 勾选收定金 → 保存。

```
耗时 5s，卡片 0→1，定金 已收 30
```

远低于 3 分钟。真正拖时间的不是点选，是老板临时找客户——所以建单抽屉里留了「回车快速建档」。

### 2 · 连做

一单两个项目（法式 90 + 延长 120）：

```
planned=210 分钟，占用 230 分钟（含缓冲 20），项目 2 个
```

`end_at = start + Σ项目时长 + 缓冲`，和 brief 的 90 + 120 + 缓冲一致。

### 3 · 改期

- 距开始 107 小时（>48h）首次改期：`free=true / changed=true`；
- 紧接着再改：停在 `needDeposit=true`，未改期，话术「免费改期已经用过，改期需扣 30 元定金：请选择退还/没收/仍免费」；
- 距开始 19 小时改期：同样停在 `needDeposit=true`；
- 该单随后「退定并撤销」：`CANCELLED`，定金 `REFUNDED`。

### 4 · 插队

构造场景：先取消 10:00 那单，而 12:10 还有一单，所以 10:00 起的空档只剩 130 分钟。

```
180 分钟：HTTP 409「空档不足：从该时刻起只剩 120 分钟，本单需要 200 分钟（含缓冲 20 分钟）」
90 分钟：2026-11-12 10:00:00 → 11:50:00，来源 JUMP
```

（「只剩 120」是扣掉 10 分钟缓冲口径的表述：130 − 10 = 120，需要 180 + 20 = 200，仍然不够。）

### 5 · 冲突

同段再建一单 → 409 + 冲突单摘要（「撞上的单：」）；点「仍然强排」后两单都在时间轴上：

```
卡片 2 张，页面提示「⚠ 2 单时段冲突，已标红」，标红 2 张
```

数据一条没丢，只是把冲突摆到明面上。

### 6 · 财务

一天 3 单，其中 1 单爽约、定金没收；另记一笔尾款收入与一笔买料支出：

```
收入 168 / 支出 58.5 / 净 109.5 / 定金没收 30 / balanced=true
```

概览（SQL 聚合）与三本明细（逐笔累加）一致。

### 7 · 物料

一单领用两种料：胶A 1 瓶（成本 45）、赞助亮片 2 包（成本记 0）。

```
胶A 成本 45（库存 3→2），赞助亮片 成本 0 / 赞助商 甲油品牌B / 价值 200
```

赞助物料成本归零、赞助信息另外记，账上不把赞助算成支出。

### 8 · 移动端

390×844：

```
scrollWidth=390 / viewport=390，时间轴 360px / 可见高度 797px
```

无横向滚动，当天时间轴一屏装得下。

### 9 · 删除客户

建客户 + 一单 → 删除客户：

```
预约仍在（id=175），卡片显示「客户已删除」，客户搜索命中 0 条
```

**这一条抓住了真问题**：原来软删除只置了 `deleted=1`，接口也返回了 `clientDeleted=true`，但 `clientNickname` 还是原昵称——前端卡片照原样显示真名，等于「标记」没落地。已修：`BookingService.toResponses` 在客户被软删除时把昵称换成「客户已删除」，短号保留可追溯。

### 10 · 构建

```
npm run build   -> exit 0（4.79s）
mvn package     -> exit 0（Tests run: 12, Failures: 0；BUILD SUCCESS）
```

`mvn package` 顺带验证了 12 例单测与可执行 jar 的打包。

## 遗留与说明

1. **改期后的「待通知清单」**目前只在排期页展示与标记，P7 的提醒清单还没有把它并进「今天要发的微信」——如果要做，是一条很小的增量（把 `notified=0` 的变更按日期塞进对应分组）。
2. **完成单不自动写尾款收入**：仍然由老板「记一笔」。这是刻意留的手动环节，避免金额算错时对不上账。
3. **没有做的**：在线支付、客户自助端、小程序、评价体系、营销分析、多美甲师排班、自动排班算法、复杂权限（brief 的「明确不做」）。
